## 1. 执行原则

1. 先保证安全、告警正确性和数据可恢复，再扩展功能或增加并发。
2. 保留单机模块化架构与 SQLite；没有容量数据，不更换数据库或拆微服务。
3. 每个问题做独立、可回滚的小变更；优先补“修复前失败、修复后通过”的回归测试。
4. 不将本次审查脚本当成产品测试：它验证现存错误行为，修复后必须转换断言。
5. 持久化路径、schema、会话和模型加载策略的变更必须说明迁移与回滚。
6. 下面的角色是建议职责，不表示已指派人员；工作量需要在确认部署方式、硬件与业务目标后估算。

## 4. 性能与质量验收：先定义，后优化

### 4.1 应采集的基线

| 维度 | 测量内容 |
|---|---|
| 摄像头 | 每路采集 FPS、真正推理 FPS、重复/过期丢帧、帧龄 P50/P95/P99、断流恢复时长 |
| 模型 | 每模型延迟、排队时间、并发数、错误率、CPU/GPU/RAM/显存峰值 |
| API | 无负载与上传/训练并行时的 P50/P95/P99、超时、错误率、在途请求数 |
| 存储 | 1 万/10 万文件分页延迟、扫描次数、实际卷剩余容量、写失败和清理耗时 |
| 训练 | 输入版本、队列/运行时间、终止耗时、重启后状态、产物完整性 |
| 业务 | 按规则/摄像头/场景的精确率与召回率、每日误报、漏报案例、端到端告警时延 |
| 运维 | 备份/恢复耗时、数据一致性校验、目标 RPO/RTO 和最近演练结果 |

现有告警的人工复核可以估计“已告警样本的误报情况”，但**不能仅凭告警记录算漏报率/召回率**；需要额外标注包含未告警时段的代表性视频。

### 4.2 建议的试验设置（不是当前性能承诺）

- 固定硬件/操作系统/依赖/模型哈希/分辨率/规则版本，对比 1、4、8 路输入；硬件不足时降低矩阵，不强制支持 8 路。
- 分别测空闲、在线检测、加测试台、加批量预标注、加训练五组负载。
- 先运行短基线和故障实验，通过后做 24 小时稳定性试运行；24 小时只是建议观察窗口，不是本次已测结果。
- 产品与业务方先填入可接受帧龄/告警时延/误报漏报门槛，再决定 batch、并发或模型压缩。
- 不接受“平均 FPS 提高，但 P99 帧龄恶化或漏报增加”的单指标优化。
